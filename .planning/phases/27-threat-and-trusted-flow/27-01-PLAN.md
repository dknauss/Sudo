# Phase 27 Plan 01 — Handoff and XSS Decision

## Objective

Select—or reject—a trusted confirmation and action-authority handoff for the
two-effect demonstrator. Derive the permitted XSS claim from observed browser
behavior. Do not implement the production proof primitive in this plan.

## Inputs

- `.planning/action-gate-architecture-charter.md`
- `.planning/REQUIREMENTS.md` (`ARCH-02`, `TRUST-01..04`, `UX-02A`)
- `.planning/phases/27-threat-and-trusted-flow/27-CONTEXT.md`
- WP Sudo's shipped challenge and in-editor flows as negative and UX evidence
- `poc/install-package-gate` and the tagged `consequential-actions` MVP as
  historical evidence only

## Fixed action descriptors

The experiments use only:

1. `core/upload-extension-package`
   - actor and login-session identity;
   - package kind: plugin or theme;
   - exact archive-byte digest;
   - server-owned display name derived without executing the archive; and
   - destination/effect class.
2. `core/write-extension-file`
   - actor and login-session identity;
   - plugin or theme identity;
   - canonical relative file path;
   - exact proposed-byte digest; and
   - destination/effect class.

The experiment may refine field encoding, but it may not add another action.

## Candidate flows

Evaluate these independently:

1. same-document modal;
2. isolated top-level confirmation;
3. isolated popup with `noopener` and a constrained return channel; and
4. browser-mediated WebAuthn/passkey confirmation.

For each candidate, record:

- where credentials and final action details render;
- which document initiates confirmation;
- which document can navigate or message which other document;
- when confirmation occurs relative to issuance and redemption;
- what crosses back to the original page;
- whether that material is readable by JavaScript;
- whether JavaScript can exercise it without reading it; and
- how the final server request proves the approved digest.

## Experiment matrix

Each candidate must produce a browser result for:

| Attacker operation | Required observation |
|---|---|
| Read | Can compromised parent script read credentials, confirmation data, or returned authority? |
| Invoke | Can it trigger the trusted flow or use authority without the user's final approval? |
| Redirect | Can it navigate the approval surface or victim browser to an attacker-selected matching action? |
| Replay | Can captured state authorize a second request? |
| Redeem | Can it cause redemption for a request the trusted surface did not approve? |
| Mutate | Does changing the target, path, or bytes after approval fail at the server digest check? |
| Clone | Can Browser B, holding Browser A's pre-challenge auth cookie and arbitrary valid WP nonces, obtain or redeem Browser A's authority? |

Every positive security result needs a deliberate mutation that makes its named
guard fail. “The broad suite went red” is insufficient; the expected guard test
must fail for the expected reason.

## Work sequence

1. Create `27-HANDOFF-DECISION.md` with the attacker traces and candidate
   sequence diagrams before writing the spike.
2. Add a research-only Playwright fixture that models the four browser
   relationships without changing WP Sudo production behavior.
3. Run the matrix first against the same-document modal as the expected negative
   control.
4. Run the isolated top-level and popup candidates.
5. Evaluate WebAuthn/passkeys only for properties the local browser harness can
   reproduce; label any hardware/provider assumption instead of simulating it
   away.
6. Record raw browser observations and focused mutation results.
7. Select a handoff or record that none is adequate.
8. Derive the demonstrator headline from that result:
   - general active-XSS language only if every in-scope active-XSS case passes;
   - otherwise the exact copied-cookie or persistence/reach-limited property.

## Stop conditions

Stop Phase 27 and do not begin Phase 28 if:

- authority is ambient to same-origin requests and confirmation does not control
  issuance or redemption;
- the original page can substitute the approved digest or destination;
- Browser B can redeem Browser A's authority;
- a claimed guard has no focused test that its mutation kills;
- the candidate depends on an unstated XSS persistence/reach assumption; or
- no candidate supports a useful, accurately worded claim.

A narrowed claim is success. A smooth but untrustworthy modal is not.

4. Selected confirmation/issuance/redemption ordering
5. Exact accepted and rejected security claims
6. Recommendation to proceed to Phase 28 or stop
